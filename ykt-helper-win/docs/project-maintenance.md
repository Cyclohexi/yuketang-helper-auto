# 项目同步与维护

仓库根目录的 `AGENTS.md` 是项目记忆入口，本文件是每次同步时调用的清单。规则和文档随 Git 拉取到其他电脑；运行数据、依赖和打包产物不随 Git 同步。

## 同步步骤

1. 读取 `AGENTS.md`，确认当前分支、`git status` 和远程状态；有未提交修改时先保存。工作区干净时可用 `git pull --ff-only` 获取更新，遇到分叉或冲突先处理，不强制覆盖。
2. 完成功能及对应测试，更新下表中受影响的文档。只有计划进入便携版的重要用户功能、明显修复及必要升级提示才追加到 `changelog.md` 的“未发布”；源码与个人开发维护变化按需更新开发文档或[开发变更记录](development-changelog.md)，不修改旧版本的发布事实。
3. 在 `ykt-helper-win` 执行 `npm run sync:check`。默认比较当前工作区与跟踪分支，包含尚未提交的新文件；指定基线可用 `npm run sync:check -- --base <提交号>`。
4. 核心逻辑变化运行 `npm test` 和 `npm run build`；检查修改文件的 lint，涉及启动入口时执行实际启动。检查 `git diff`，确认没有无关修改或真实用户数据。
5. 明确列出本次文件进行提交并推送。最后核对本地 HEAD 和远程分支提交一致；其他电脑开始开发前拉取。仅同步文档不需要重新打包。

## 按改动范围更新

| 改动                                 | 同步文档                                                          |
| ------------------------------------ | ----------------------------------------------------------------- |
| 计划进入便携版的重要用户功能与修复   | 根 README、changelog                                              |
| 仅源码、个人调试及开发维护变化       | 核心工程 README、相关开发文档，必要时 development-changelog.md    |
| 启动脚本、依赖、编译、调试、维护命令 | 核心工程 README                                                   |
| 数据路径、迁移、架构、长期维护决定   | 项目知识库、核心工程 README，必要时 AGENTS                        |
| 自动更新、打包、发行格式             | auto-update.md、desktop/README.md、用户说明                       |
| CLI、作业详情、字体、网络实验室      | 对应专项文档；只有内容受影响时才修改                              |
| 正式 Release                         | 同版本发布说明、changelog、README 版本记录、package.json 与锁文件 |

`sync:check` 会读取项目记忆、检查必要文件、工作区版本一致性、真实数据是否被跟踪，以及常见源码变更是否补充基本文档。它不能从任意代码准确判断产品含义，仍须人工核对上表；不自动改写说明，不自动提交或发布。

公开更新范围适用于 README 版本记录、根 changelog、GitHub Release 与应用自动更新说明。不要把 Git 提交或开发记录整段搬进发布说明；先筛选用户实际需要知道的变化，再合并成少量条目。BAT 启动、个人调试、配置目录维护、清理、项目记忆及同步检查不写成公开更新。v2.2.1 展示题目预分析及相关提醒、请求失败自动重试、截止未提交自动强制补交及独立开关，并按 2026-10-22 用户最新指令增加一条“修复自动更新”。后续版本仍须先同步源码，再按用户确认的范围发布。必要的数据迁移与使用限制可在对应使用说明中维护，正式升级确有必要时再提供精简提示。

## 数据与测试

Windows 固定数据根目录为 `%LOCALAPPDATA%\YuketangHelper`，通常位于 C 盘。`storage/yuketang.sqlite` 保存设置及应用数据，`storage/credentials.json` 为加密凭据，`Partitions` 等保存网页会话，`Cache` 等为浏览器缓存，`storage/resource-cache` 为课件资源缓存，`updates` 保存更新任务。它们均在程序目录之外。

源码、根目录 BAT 和新版 EXE 使用同一路径；`--portable` 不再切换数据位置。`npm start -- --debug-profile` 使用同级的 `YuketangHelper-debug`，不读取或复制正式配置。测试版本若修改数据库结构，先备份正式数据，并验证降级兼容；Git 回退不会撤销数据变更。

第一次启动新版时，仅当固定目录不存在，才从旧目录复制完整 profile：优先已有设置或用户记录的数据，同等级选择数据库较新的数据，不混合多个数据库。复制成功才启用新目录，原目录原样保留。已有固定目录后不再导入旧目录。旧版程序应先关闭，以便数据库和浏览器会话完整落盘。`data-migration.json` 只记录来源与时间，不记录密钥。

迁移期间存在同级 `YuketangHelper.migration-pending.json` 标记；完成后才移除。复制失败或中断时保留该标记，下次启动会拒绝使用半成品。此时应关闭旧版后从原目录恢复，不能只删除标记而继续使用不完整数据。

旧版 v2.2.0 及更早程序仍按各自原有规则读取数据；只有使用本次改动构建的程序才使用固定目录。Windows 加密凭据与系统用户有关，跨电脑复制后可能需要重新登录或输入密钥。

## 回退与发布

每项功能使用独立提交，必要时在 `codex/` 分支与单独 worktree 迭代。撤销已推送的错误使用 `git revert` 保留历史。需要复现旧版时从标签创建独立目录，避免改动正在工作的主目录。

发布按 `auto-update.md` 操作：验收代码、设置递增版本、更新文档、从固定提交构建、打标签、上传并校验草稿，再按用户的发布指令公开。只有 ZIP 和更新清单进入正式附件；公开版本不覆盖，代码回滚后的修复也使用新版本号。

本次例外：2026-10-22 用户明确要求替换 v2.2.1 为修复自动更新的同版本包，允许同步修订公开说明、附件与标签。先保留旧标签所指提交和原附件备份，完整构建并校验新附件，发布时核对标签与源码一致。须明确提示原 v2.2.1 用户手动替换一次；同版本不会触发升级。此授权不改变后续版本默认递增的规则，普通上传脚本仍拒绝覆盖已公开版本。

## 保持目录清爽

- 保留源码、测试、锁文件、文档、静态图片、Git 历史、最新可运行本地 EXE、正式发行 ZIP 与清单、所有用户数据及备份。
- `desktop/.electron-cache` 可重新下载，`desktop/out/make` 是 ZIP 中间产物；确认正式附件已在 `desktop/out/release` 保留后可清理。
- `desktop/out/*-win32-x64` 是解包构建产物。仅当日常使用目录已保存并验证同一份新程序，且构建目录没有用户数据时，才可清理这个额外副本；保留日常可运行程序。
- 依赖用 npm 管理，确认多余依赖后清理并重新验证构建；不能按目录名字随意删除运行库或共享包。
- 删除前检查最终绝对路径在项目根目录内；发现 `ykt-helper-data`、凭据或其他用户文件时保留。禁止用 `git clean -fdx` 清理整个仓库。
